# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

TicketMan is a ticket-tracking app for repair shops. It is a Kotlin Multiplatform project: a Compose Multiplatform client (desktop is the primary, most complete target) talking over HTTP to a Ktor server backed by an H2 database via Exposed. Package root everywhere is `org.mr0btain.ticketman`.

Developer docs live in `docs/` (index: `docs/README.md`), with longer explanations of what's summarized here. `docs/PLAN.md` tracks which pages are written. When a change makes a doc page wrong, fix the page too, and follow `docs/STYLE.md` when writing one. `docs/decisions.md` says why some choices were made (H2, per device sessions, delayed photo deletion, ...); read it before undoing one. `docs/FIX-PLAN.md` is the phased list of known issues to work through; tick items there (and remove them from their page's Known gaps) as they're fixed.

## Commands

Use `./gradlew` (Git Bash) or `.\gradlew.bat` (PowerShell).

```bash
./gradlew :composeApp:run                    # Run desktop client (main: org.mr0btain.ticketman.MainKt)
./gradlew :composeApp:hotRunDesktop --mainClass org.mr0btain.ticketman.MainKt --auto  # Desktop with Compose hot reload
./gradlew :composeApp:wasmJsBrowserDevelopmentRun  # Web client
./gradlew :androidApp:assembleDebug          # Android APK
./gradlew :server:run                        # Ktor server (Netty, port $PORT or 8080)
./gradlew :server:run -Pdevelopment          # Server with io.ktor.development=true (also turns on CORS for the web dev server)
./gradlew :server:run -PwithWeb              # Server with the web client built in, served at /

./gradlew :server:test                                   # Server tests
./gradlew :server:test --tests "org.mr0btain.ticketman.ApplicationTest"  # Single test class
./gradlew :shared:jvmTest                                # Shared module tests (JVM)
./gradlew :composeApp:desktopTest                        # Client tests (commonTest + desktopTest)

# End to end: start a dev server, then walk check-in -> pickup over HTTP
PORT=8098 DATA_PATH=/tmp/tm ADMIN_PASSWORD=admin_pass ./gradlew :server:run -Pdevelopment
python3 scripts/counter_e2e.py http://localhost:8098

python3 scripts/check_api_docs.py            # docs/api against the route files (--list prints every endpoint)
```

There is no lint task configured; `docs/testing.md` covers the test helpers in detail. Server tests live in `server/src/test`, client tests in `composeApp/src/commonTest` (network repos use Ktor's `MockEngine`; handlers take a `RemoteHandler` built on one) and `composeApp/src/desktopTest` (Java2D printing, ZXing-checked QR codes, UI renders, and `UiKitRulesTest`). `KitGalleryRenderTest` and `ScreenRenderTest` draw the component gallery and the main screens with sample data to PNGs in `composeApp/build/kit-gallery` and `composeApp/build/screen-renders`, which is the quickest way to look over a UI change without running the app. `testApplication` doesn't load `application.yaml`, so server tests use the helpers in `server/src/test/.../TestServer.kt`: `createTestDataDir()`, `configureTestServer(dataDir)` (supplies `env.dataPath` and `jwt.*` via `MapApplicationConfig`), and `cleanupTestDataDir(dataDir)` in `@AfterTest` (shuts H2 down, then deletes the dir). `AuthTest.kt` shows the login → bearer request → refresh flow. `RestoreTest` shows how to restart the server on the same data dir (two `testApplication` blocks with an H2 `SHUTDOWN` between). The in-process test engine doesn't behave like Netty for big or cut-off request bodies, so check upload and download changes against a real `:server:run` too.

Server config lives in `server/src/main/resources/application.yaml`, overridable by env vars: `PORT` (plain HTTP), `SSL_PORT` (HTTPS, default 8443, `0` turns it off), `HTTP_MODE` (`on`/`redirect`/`off`; blank means `redirect`, or `on` in development mode), `SSL_KEYSTORE` + `SSL_KEYSTORE_PASSWORD` (+ `SSL_KEY_ALIAS`, `SSL_KEY_PASSWORD`) for a supplied PKCS12 certificate, `CORS_HOSTS` (development mode only), `SECRET` (JWT secret; when unset the server makes one and keeps it in `<dataPath>/server/secret`, see `ServerSecret`), `TRUST_PROXY` (`true` behind a reverse proxy, so limits use `X-Forwarded-For`), `NAME`, `DATA_PATH` (where the H2 DB is created; falls back to the platform `AppDir`), `ADMIN_PASSWORD` (password for the `admin` user created on start when no admin exists; a random one is logged if unset). `Application.module()` contains a `generateTestData` flag that seeds the DB via `seedTestData()`; on a server started with `-Pdevelopment` admins can also seed from the admin screen.

## Modules

- **`shared`** — KMP library (android, jvm, wasmJs; iOS targets commented out). Holds everything both client and server need: `@Serializable` domain models (`data/`), request/response DTOs (`server/request`, `server/response`), the `Result<D, E: Error>` type + per-domain error enums (`error/`), caches, and `expect` declarations (`AppLogger`, `AppDir`, `Platform`) with per-platform `actual`s.
- **`composeApp`** — KMP Compose UI + client logic, built as an Android *library* plus `jvm("desktop")` and `wasmJs`. iOS targets are commented out.
- **`androidApp`** — thin Android application wrapper around `composeApp` (`MainActivity`).
- **`server`** — Ktor JVM app (`EngineMain`, module `ApplicationKt.module`).
- **`iosApp`** — Xcode project; currently not wired up since iOS targets are disabled.

Dependency versions and bundles (`ktorServer`, `ktorClient`, `exposed`, `koin`, `fileKit`) are in `gradle/libs.versions.toml`. Projects are referenced via type-safe accessors (`projects.shared`).

## Architecture

### Domain model pattern
Each main entity (Customer, Ticket, Inventory, User) extends `MainItem` (shared), identified by a `Uuid` whose embedded timestamp is used as the creation time (`identifier.createdAt()`). Entities have attached `Note`s, and notes have `StoredImage`s. This shape is mirrored identically on each layer, so adding a field or entity usually means touching all of them:

1. `shared/.../data/<entity>/` — serializable model
2. `server/.../database/tables/<entity>/` — Exposed DAO tables/entities (plus `<Entity>NoteTable`, join tables), registered in `LocalDatabase.initDatabase()`'s `SchemaUtils.create(...)`
3. `server/.../database/<Entity>Database.kt` — extends abstract `Database<T : MainItem>` (CRUD, paging, notes, images, search)
4. `server/.../routing/<Entity>Route.kt` — mounted under `/api/data/<entity>` (users under `/api/user`, auth under `/api/auth`, admin dashboard under `/api/admin`, shop profile under `/api/shop`) in `Routing.kt`
5. `composeApp/.../network/database/<Entity>RemoteRepository.kt` — extends abstract `RemoteRepository<T>`, whose route paths (`/add`, `/fetch`, `/get`, `/update`, `/remove/{id}`, `/search`, `/get/notes/{id}`, ...) must match the server route
6. `composeApp/.../data/<entity>/` — client-side `*Cache` and `*Seed`. A seed is the record being viewed or edited: each one lists its editable `fields()`, and `isDirty` / `getChangedFields()` compare them against the snapshot `markClean()` took when it was loaded or saved, so changing something back counts as unchanged. A new field only needs adding to `fields()`

### Server
`Application.module()` → `configureDatabase(path)` builds a `LocalDatabase` (H2 file DB at `<path>/server/database/`) exposing one `<Entity>Database` per entity plus `TokenDatabase`. `JwtService`/`UserService` handle login and access/refresh tokens. Passwords and PINs are PBKDF2-hashed by `PasswordHasher` (legacy plain-text passwords are upgraded on login) and users are blanked with `User.withoutPassword()` before leaving the server. Write routes log to `AuditLogDatabase` via `call.audit(...)`.

- **Sessions**: one row per device in `TokenTable` (`TokenDatabase`/`StoredSession`). Tokens carry a `sid` claim, a `typ` (`access`/`refresh`) and a random `jti`; the auth providers only take access tokens, valid only while that session row exists for its user and is live (`StoredSession.isLive`: before `expiresAt`, and within a kiosk PIN session's idle limit). Each refresh swaps the refresh token for a new one with the same expiry (`TokenDatabase.rotate`, a compare and set), and the client saves it. The hourly sweep deletes expired sessions (`removeExpired`). A good token whose access level is too low gets `403` (`JwtService.checkAccess` → `AccessCheck.Denied`), anything else turned away `401`. Wrong password logins are capped in memory (20 per address, 10 per username per 15 minutes, `429` after). The client sends a stable `deviceId`, so logging in again on the same device replaces its session; other devices are untouched.
- **Users**: `UserStatus` (PENDING/ACTIVE/DEACTIVATED) is separate from `AccessLevel`; `User.canAccess(level)` is the check (active, setup finished, level high enough). `AccessLevel.NONE` only exists for migrating old data. New accounts come from requests (`/api/auth/request-account`, then admin approve) or invites (setup code used as the password), see `AccountService`. Users with `needsSetup` can only reach routes under the `"setup"` auth provider.
- **PINs and stations**: 6 digit PINs (`PinRules`) lock after 5 wrong tries. PIN login (`/api/auth/pin`) needs an admin-approved station's id + secret (`StationDatabase`); PIN sessions last 12h and each one ends the previous PIN session on that station. Stations can be put in kiosk mode with an idle timeout; a kiosk's PIN session also ends on the server once unused for that timeout plus 10 minutes (the client keeps it alive while someone is using it), and an admin leaving kiosk mode calls `/api/auth/kiosk/leave` to drop that limit.
- **Money**: always `Long` cents (`Money` in shared). Invoices (`InvoiceDatabase`/`InvoiceService`) are one per ticket; totals come from shared `InvoiceMath`, tax from the shop profile. `POST /api/counter/pickup` pays the invoice, takes parts from stock (refusing if there isn't enough) and closes the ticket together. Stock never goes below zero and only changes in single SQL updates: pickup and void through `InventoryDatabase.adjustStock`, and by hand through `/api/data/inventory/set/stock/{id}`, which only writes if the count is still the `from` the client opened it at (409 otherwise). Inventory `/update` leaves stock alone; `InvoiceService` changes that check then write run under its `CHANGE_LOCK`, so two pickups can't both go through. Only pickup sets `PICKED_UP`: ticket add/update refuse it and never change a picked up ticket's status; `POST /api/counter/check-in` makes the ticket, links, deposit and signature together (`CheckInService`).
- **Numbers**: tickets `26-00000042` and invoices `INV-26-00000042`, per year, assigned under a lock with a unique index. An outer transaction that adds a ticket or invoice (check-in) has to hold the lock until it commits: `tickets.whileNumbering { invoices.whileNumbering { transaction { ... } } }`, ticket lock first.
- **Photos**: bytes live on disk in `ImageStore` (`<dataPath>/server/images/<first 2 chars of id>/<id>/{original,display,thumb}.jpg`), with paths built only from the id and never from client input. Only metadata goes in `ImageTable`. `POST /api/image/upload` (multipart, `ImageLimits`: 25 MB, 50 MP) goes through `ImageService`/`ImageProcessor` (Thumbnailator), which rotates the photo upright from EXIF, strips its metadata, flattens transparency and writes the `ImageVariant` sizes (2560/1600/320, never enlarged). Uploads start `PENDING`, and only the uploader can fetch a pending photo. Saving a note or inventory item links them through `linkImages()`, which only takes photos that are pending or already on that owner. Dropped photos are soft deleted (`DELETED`). Photos never change once uploaded, so `GET /api/image/{id}/{variant}` sends an immutable `Cache-Control` and its hash as the ETag. Never delete photo files directly: mark rows deleted (`markImagesDeleted`) and leave it to the hourly `ImageService.sweep()`, which purges after a day and also removes orphan folders. Notes are edited in place with `/update/note/{id}`; inventory photos are set as a whole list with `/set/images/{id}`.
- **Backup and restore**: `BackupService` builds a zip on disk (`manifest.json`, `database.zip` from H2 `BACKUP`, optionally `images/`) and returns a `BackupTicket`. Its link `/api/admin/backup/download/{id}?token=` needs no login (the browser can download it directly), lasts 30 minutes, or 5 minutes after it was last used, and supports Range. The database is copied before the photos, which is consistent only because photo deletion is delayed a day. `POST /api/admin/restore` (raw zip body) validates the archive and parks it in `server/restore/`. `RestoreService.applyPending()` runs in `configureDatabase` before H2 opens: it moves `database/` and `images/` to `pre-restore-<time>/` and unpacks the archive, rolling back on failure. Restoring always needs a restart. Big bodies are streamed with `copyToFile` / `respondFile`, never `receive<ByteArray>` / `respondBytes`.
- **HTTPS**: `main()` calls `createServer(args)`, which is Netty's `EngineMain` setup plus an `sslConnector` on `tls.port`. The certificate comes from `ServerTls` (`components/tls/`): the supplied `SSL_KEYSTORE` (a bad one stops the server) or one it makes once in `<dataPath>/server/tls/` (10 years, kept, since devices pin it). The fingerprint is logged on start and shown on the admin Server tab (`ServerInfoResponse.certificate`); `formatFingerprint` in shared is the one format everywhere. `HTTP_MODE=redirect` installs `HttpsRedirect` (`plugins/Https.kt`); clients with an `http://` address see the redirect when connecting and move to the `https://` one (`ServerUserClient.httpsRedirectOf`, saved through `SessionHandler`'s `onServerMoved`). `GET /api/ping` answers `TicketMan` and is the clients' up check (`/` stays as the old one when no web client is built in). With `-PwithWeb`, `server/build.gradle.kts` copies `:composeApp:wasmJsBrowserDistribution` into resources `web/` with `.gz` copies, and `webRoute()` serves it at `/`. CORS (`plugins/Cors.kt`) is only installed in development mode.
- **Access**: read routes use `authenticate("restricted")` so Restricted users can look; writes use the default (NORMAL) provider. `UsernameRules`, `PasswordRules` and `PinRules` are in shared and checked on both sides.
- **Notes**: every record type mounts the shared `noteRoute` (`/add/note/{id}`, `/get/notes/{id}`, `/update/note/{id}`, `/remove/note/{id}`). Update and remove take only the note's id, so `Database` checks the note is on that record type (`noteLinkColumn`) before changing it. Staff notes on users (`/api/user/...`) are admin only for reading and writing, and are saved and deleted straight away by `UserRecords` and shown in the admin Users tab. Notes and their photos are edited and deleted in the kit's `TmEditNoteDialog`; on records the change is only sent when the record is saved, and record dialogs keep Save off until `seed.isDirty`.
- **Migrations**: `LocalDatabase.initDatabase()` creates tables, then adds missing columns only for tables in `migratedTables` (add a table there when you give it a column; new columns need a default or nullable). Columns on the `user` table go in `addUserColumns()` because H2 can't list that table's columns (reserved word). Avoid reserved column names (`condition` is stored as `device_condition`). Data fixes run after (`backfillNumbers`, `migrateDeactivatedUsers`, `clearLegacySessions`, `migrateLegacyPrices`, `removeDetachedNotes`). `plugins/Security.kt` registers three JWT auth providers keyed to `AccessLevel`: default (`NORMAL`), `"restricted"`, and `"admin"`; routes wrap handlers in `authenticate { }` / `authenticate("admin") { }`. `routing/Helpers.kt#getIdentifierFromToken()` extracts the calling user's UUID from the JWT.

### Client
- DI: Koin, started in each platform entry point via `initKoin()` with `viewModelModule` and `dataModule`.
- `ui/MainViewModel` is the app-lifetime state holder. It owns the `RemoteHandler` and wires together handlers that each own one part of the app, connected through callbacks: `CustomerRecords`/`TicketRecords`/`InventoryRecords`/`UserRecords` (`viewModel.customers` etc., in `ui/screens/records/components/<entity>/`: each entity's cache, `OffsetPager`, seed, selection, save, remove and search; notes sync through `syncNotes` in `RecordNotes.kt`), `SessionHandler` (`viewModel.session`: connecting, login/logout, the logged-in `currentUser`/`isAdmin`/`canEdit`, account requests and setup, this device's station), `SettingsHandler` (`viewModel.settings`: saved settings, each change written to `LocalStorage`), `AdminHandler` (admin screen), `CounterHandler` (counter: search, queue, ticket card, check-in, pickup, invoices, printing) and `KioskHandler` (kiosk mode, PIN lock, idle timer). `CounterHandler` and the customer, ticket and inventory records handlers take `canEdit` and refuse changes for Restricted users, and their screens hide the buttons (`TmPanelTopBar(canChange = false)` shows a "View only" badge, `RecordDetail(canEdit = false)` drops Edit); the server still refuses the write.
- Counter screen is `ui/screens/counter/`. Kiosk mode (`ui/screens/kiosk/`) replaces the whole app with the counter and a PIN lock screen; it turns off `RemoteHandler.credentialFallback` so a locked kiosk can't log the owner back in, and sets `ui/AppWindow.fullscreen`, which each platform entry point applies.
- Photos: `ImageClient` (handed to composables via `LocalImageClient`, null in previews and render tests) uploads picked files; only Android shrinks them first, because FileKit's desktop compressor ignores EXIF orientation. It also builds the Coil `ImageLoader`, set as the singleton in `App`, which fetches through `RemoteHandler.httpClient` so photo requests carry the bearer token, with a 250 MB disk cache via `imageDiskCache()` (none on web). Show photos with the kit's `TmImage` / `TmImagePager` / `TmImageView` and edit them with `TmPhotoEditor` (all in `ui/kit/images/`).
- Large transfers: the HTTP client logs headers only (logging bodies buffers them) and has a 60s request timeout. Long uploads and downloads call `transferTimeout()`. `components/network/transfer` holds `downloadTo` (streams to a kotlinx-io sink), `saveDownload` (file saver on desktop/Android, browser download on web) and `fileBody` (streams a picked file as a request body; web reads it whole). Use these rather than `readRawBytes` + `saveFile` for anything that can be big.
- Printing: `components/print/PrintTemplates` builds a platform-neutral `PrintDocument`; `printDocument()` is expect/actual (desktop: Java2D `PrinterJob`; web: hidden iframe of `HtmlPrintRenderer`; Android: WebView + `PrintManager`, needs `AndroidPrintHost.attach` from `MainActivity`). `QrCode` is an in-house encoder.
- Times on screen go through `components/utils/Formatting.kt` (local time via kotlinx-datetime).
- `RemoteHandler` builds a Ktor client (with bearer-token auth/refresh using `LocalStorage`) and holds one remote repository per entity; `setUrl()` verifies the server is reachable and propagates the base URL to every repo. Repositories no-op when `serverUrl` is blank.
- `LocalStorage` persists settings/tokens through a `KeyValueStore` (KSafe-backed; `InMemoryKeyValueStore` in tests).
- UI: every screen is built from the UI kit (below). `ui/screens/navigation/AppShell.kt` frames the app: a glass nav rail on wide windows (`WideAppShell`, with the user menu and log out at its foot) or a glass bottom bar on phones (`PhoneAppShell`), the backdrop behind everything and the snackbar host. The records screen (`ui/screens/records/`, `Destination.RECORDS`) is one `RecordsLayout` per entity: toolbar (the kit's `TmPanelTopBar`), list, and details, stacking on narrow windows.
- Server trust: addresses with no scheme mean `https://` (`normalizeServerAddress`); addresses saved before HTTPS get `http://` added once when `LocalStorage` loads. Desktop and Android share `jvmSharedMain` (a `jvmShared` group in `applyDefaultHierarchyTemplate`), which holds the OkHttp engine: `PinningTrustManager` accepts what the system trusts plus the one fingerprint `ServerTrust` holds per `host:port`, and refuses anything else into `ServerTrust.refused`. `setUrl` then returns `ConnectionResult.UNTRUSTED`, and `App` shows `ServerTrustDialog` for `SessionHandler.untrustedCertificate`; trusting saves the fingerprint (`trusted_certificates`). Web uses Ktor's Js engine and the browser decides. Test mocks must answer `SERVER_PING_PATH` with `SERVER_PING_BODY`.
- Platform specifics go through `expect`/`actual` (`getHttpEngine`, `defaultServerAddress`, `IsDebug`, `InitAppDir`, `TmVerticalScrollbar`, `AppLogger`, `saveFile`, `printDocument`, `shrinkForUpload`, `imageDiskCache`, `saveDownload`, `fileBody`).
- `androidApp` currently needs compileSdk 37 to build (FileKit 0.16 requires it); `shared` and `composeApp` compile for Android with `:composeApp:compileAndroidMain`. Building the APK needs an AAPT2 that runs on the build machine (the x86 Linux one Gradle downloads fails on ARM Linux). Android and web compile but haven't been run end to end yet. `isDebug()` is the debuggable flag on Android, a `localhost` page on web, and `-DticketmanDebug=true` on desktop.

### UI kit
All shared UI lives in `composeApp/src/commonMain/.../ui/kit/`, prefixed `Tm`: `theme/` (tokens), `foundation/` (backdrop, glass and solid surfaces, hover/press/focus, control sizes, scrollbar), `buttons/`, `inputs/` (text, money, PIN, password, signature), `selection/` (dropdown, menu, segmented, chips, toggles), `search/`, `containers/` (panel, dialog, confirm, confirm delete, text edit and full screen dialogs, page and pane headers, list rows, tabs, lazy and scroll columns), `feedback/` (badges for ticket status, priority, access, notices, snackbar, empty and loading states), `data/` (stat tiles, tables, money and ticket number text, key value rows), `images/` (photo, pager, full screen viewer, photo editor), `notes/` (note block, edit note dialog), `navigation/` (rail, top bar, records panel top bar, bottom nav, stepper) and `gallery/` (the component gallery, opened from Settings > Appearance, and in the nav on debug builds).
- Screens get colors, type, shapes and spacing from `TmTheme.colors/typography/shapes/spacing` and never hard code them. `UiKitRulesTest` fails on `Color(0x`, `fontSize =`, `RoundedCornerShape(`, `MaterialTheme.` or Material component imports (other than `Text`, `Icon`, `SnackbarHostState`) outside `ui/kit`. Need something new? Add it to the kit and the gallery, then use it.
- Themes: `TmPalettes` (Bench default, Copper, Mono), each with dark and light `TmColors`; add one by adding a `TmPalette` to `TmPalettes.all`. Fonts: `TmFonts` (Barlow default, Atkinson Hyperlegible, System); add one by putting its `.ttf`s in `composeResources/font` and a `TmFont` in `TmFonts.all`. Numbers (ticket and invoice numbers, money, PINs, SKUs) always use the `numeric*` styles (JetBrains Mono). The picked theme, font, dark mode and reduce transparency are saved in `LocalStorage` and exposed by `SettingsHandler`.
- Glass: `TmBackdrop` owns a Haze state and draws the background glow; `TmGlassSurface`/`Modifier.glass()` blur whatever sits behind them, `Modifier.glassSource()` marks content (like a scrolling list) for glass on top to blur. Glass is for floating layers only (rail, bars, dialogs, menus, snackbar); cards and lists use solid `TmSurface`. Reduce transparency turns glass solid.
- Ticket statuses show as `TmStatusBadge` with the wording in `TicketStatusType.label` ("Ready for pickup" for DONE); tones come from `TmColors.tone(...)` so a state keeps its color across themes.

### Conventions
- Naming: UI used by more than one screen is a kit component, `Tm`-prefixed, in `ui/kit` with a gallery entry. Classes extending an abstract base get no `Impl` suffix (`TicketDatabase`, `TicketRemoteRepository`). Platform files are `<Name>.<platform>.kt` next to a common `<Name>.kt` holding the `expect`. Route files are singular, `<Area>Route.kt` with `fun Route.<area>Route()`. Each screen's state lives in an `<Area>Handler` under that screen's `components/`.
- Logging uses `AppLogger.{e,d,i,m}(tag, message)` with hierarchical string tags declared as constants at the top of each class, e.g. `"$TAG:GetById"`. Follow this pattern in new code.
- Errors: wrap client network calls in `networkRequest(TAG) { ... }` (a `Result` saying whether it timed out, couldn't connect or got an unreadable response; pass it to `handleActionHttpResponse`/`handleDataHttpResponse`) or `networkErrorTryCatch(TAG) { ... }` (value or null, for reads), shared code in `appLogTryCatch(TAG) { ... }`, and return `Result`/`SimpleResult` rather than throwing. Every error enum implements `Error` (which carries a readable `message`), so any of them can go in a `Result`.
- Server DB access goes through `dbQuery(TAG) { ... }` (returns the value, null on failure) and `dbWrite(TAG) { ... }` (returns whether it happened; the block returns false when the row isn't there) in `database/DbCall.kt`. Write methods return that `Boolean` and routes answer 404/500 from it instead of always 202. Inside an outer `transaction { }` (check-in, pickup) they let throws through, so the whole thing rolls back. Some newer databases still use `appLogTryCatch` + `transaction`.
