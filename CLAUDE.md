# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

TicketMan is a ticket-tracking app for repair shops. It is a Kotlin Multiplatform project: a Compose Multiplatform client (desktop is the primary, most complete target) talking over HTTP to a Ktor server backed by an H2 database via Exposed. Package root everywhere is `org.mr0btain.ticketman`.

Developer docs live in `docs/` (index: `docs/README.md`), with longer explanations of what's summarized here. 

## Commands

Use `./gradlew` (Git Bash) or `.\gradlew.bat` (PowerShell).

```bash
./gradlew :composeApp:run                    # Run desktop client (main: org.mr0btain.ticketman.MainKt)
./gradlew :composeApp:hotRunDesktop --mainClass org.mr0btain.ticketman.MainKt --auto  # Desktop with Compose hot reload
./gradlew :composeApp:wasmJsBrowserDevelopmentRun  # Web client
./gradlew :androidApp:assembleDebug          # Android APK
./gradlew :server:run                        # Ktor server (Netty, port $PORT or 8080)
./gradlew :server:run -Pdevelopment          # Server with io.ktor.development=true (also turns on CORS for the web dev server)
./gradlew :server:run -PwithWeb              # Server with the web client built in, served at /

./gradlew :server:test                                   # Server tests
./gradlew :server:test --tests "org.mr0btain.ticketman.ApplicationTest"  # Single test class
./gradlew :shared:jvmTest                                # Shared module tests (JVM)
./gradlew :composeApp:desktopTest                        # Client tests (commonTest + desktopTest)

# End to end: start a dev server, then walk check-in -> pickup over HTTP
PORT=8098 DATA_PATH=/tmp/tm ADMIN_PASSWORD=admin_pass ./gradlew :server:run -Pdevelopment
python3 scripts/counter_e2e.py http://localhost:8098

# Behind a reverse proxy without Docker (needs Caddy): dev server on 8080, Caddy on https://localhost:8444
scripts/dev_proxy.sh                                     # Ctrl+C stops both; --no-server for Caddy only
python3 scripts/counter_e2e.py https://localhost:8444 --insecure   # also runs the big photo, backup and restore steps
./gradlew :composeApp:run -DticketmanDebug=true -PdevTrustStore=build/dev-truststore.p12  # trust Caddy's CA, no dialog

# Docker: the image copies the server built on the host
./gradlew :server:installDist -PwithWeb && docker build -f server/Dockerfile -t ticketman .
scripts/docker_smoke.sh                                  # docker-compose.yml behind Caddy: e2e, restore by restart, clean stop
scripts/docker_local.sh                                  # the same left running at https://localhost:8443 to try by hand (--down removes it)

# Release packages (docs/releasing.md); the version is ticketman.version in gradle.properties. The build names each
# one: TicketMan-<OS>-<version>-<arch>.<ext> for the machine's own (TicketMan-Windows-0.8.0-x64.msi),
# TicketMan-Android-<version>.apk, TicketMan-Desktop-<version>.jar, TicketMan-Server[-Web]-<version>.zip/.jar
./gradlew :composeApp:packageDistributionForCurrentOS   # MSI, DMG or DEB, for the OS it runs on
./gradlew :composeApp:packageTarball                     # the desktop app unpacked, as a .tar.gz
./gradlew :androidApp:assembleRelease                    # signed when TICKETMAN_KEYSTORE* are set

./gradlew :server:buildFatJar -PwithWeb                  # the same as one jar

# io.github.Mr0btain.TicketMan, which packages the -PallPlatforms desktop jar on the openjdk21 extension
python3 scripts/flatpak.py check             # the metainfo has a <release> for ticketman.version, screenshots at its tag
python3 scripts/flatpak.py build --install   # build the jar and the Flatpak from this checkout, lint, install
python3 scripts/flatpak.py update <version>  # after a GitHub release: the manifest's jar sha256 and tag commit

python3 scripts/check_api_docs.py            # docs/api against the route files (--list prints every endpoint)
python3 scripts/check_doc_links.py           # every relative link and anchor in docs/ and CLAUDE.md resolves
```

CI (`.gitea/workflows/ci.yml`, copied to `.github/workflows/ci.yml` for GitHub) runs the three test tasks, compiles web and Android, and runs both doc checks and `flatpak.py check` on every pull request. Pushing a `v*` tag matching `ticketman.version` runs `.gitea/workflows/release.yml` (DEB, plus an arm64 DEB built through QEMU from `docker/deb.Dockerfile`, MSI on a self-hosted Windows runner, desktop jar, APK, server zips, jars and images with and without the web client) and, on GitHub, `.github/workflows/release.yml` (the same files, named by the build, with the same skip inputs and variables, tarballs, images on ghcr.io (Docker Hub is pushed only from Gitea), plus arm64 and x64 DMGs and an opt-in unsigned iOS IPA, with the arm64 DEB built on an arm64 runner), which publish a release. GitHub's CI also compiles iOS on a Mac runner.

There is no lint task configured; `docs/testing.md` covers the test helpers in detail. Server tests live in `server/src/test`, client tests in `composeApp/src/commonTest` (network repos use Ktor's `MockEngine`; handlers take a `RemoteHandler` built on one) and `composeApp/src/desktopTest` (Java2D printing, ZXing-checked QR codes, UI renders, and `UiKitRulesTest`). `KitGalleryRenderTest` and `ScreenRenderTest` draw the component gallery and the main screens with sample data to PNGs in `composeApp/build/kit-gallery` and `composeApp/build/screen-renders`, which is the quickest way to look over a UI change without running the app. `ScreenRenderTest.screen(name, rail = ...)` draws a screen both in the wide shell and at phone width (`<name>-narrow`); use it for new screens, and check the narrow one too. `testApplication` doesn't load `application.yaml`, so server tests use the helpers in `server/src/test/.../TestServer.kt`: `createTestDataDir()`, `configureTestServer(dataDir)` (supplies `env.dataPath` and `jwt.*` via `MapApplicationConfig`), and `cleanupTestDataDir(dataDir)` in `@AfterTest` (shuts H2 down, then deletes the dir). `AuthTest.kt` shows the login → bearer request → refresh flow. `RestoreTest` shows how to restart the server on the same data dir (two `testApplication` blocks with an H2 `SHUTDOWN` between). The in-process test engine doesn't behave like Netty for big or cut-off request bodies, so check upload and download changes against a real `:server:run` too.

Server config lives in `server/src/main/resources/application.yaml`, overridable by env vars: `PORT` (plain HTTP, the only thing the server speaks; HTTPS is always a reverse proxy's job, and the old `PROXY`, `TRUST_PROXY`, `SSL_*` and `HTTP_MODE` settings only get a startup warning), `CORS_HOSTS` (development mode only), `SECRET` (JWT secret; when unset the server makes one and keeps it in `<dataPath>/server/secret`, see `ServerSecret`), `TRUSTED_PROXIES` (addresses and CIDR ranges whose `X-Forwarded-For` is believed, so limits count each device; blank means loopback and the private ranges, `none` ignores it; `ProxySettings`), `TZ` (the shop's time zone; a UTC server without it logs a warning, since "today" and the yearly number rollover follow it), `RESTART_ON_EXIT` (`true` when something starts the server again after it exits, enabling `POST /api/admin/restart`, `ServerRestart`; the Docker image sets it), `NAME`, `DATA_PATH` (where the H2 DB is created; falls back to the platform `AppDir`), `ADMIN_PASSWORD` (password for the `admin` user created on start when no admin exists; a random one is logged if unset), `BACKUP_DIR` + `BACKUP_KEEP` + `BACKUP_PHOTOS` (daily backup into a folder, off when blank), `AUDIT_LOG_DAYS` (730) and `RESTORE_KEEP_DAYS` (30) for what the hourly sweep trims (`Housekeeping`; `0` keeps everything). `SEED_TEST_DATA=true` seeds an empty database on start via `seedTestData()` (tickets, customers, inventory, users, then work, deposits and pickups through `InvoiceService`, a demo shop profile, and `tech`/`tech_pass` and `clerk`/`clerk_pass`); `scripts/docker_local.sh` sets it. On a server started with `-Pdevelopment` admins can also seed from the admin screen.

## Modules

- **`shared`** — KMP library (android, jvm, wasmJs, and iOS when built on a Mac). Holds everything both client and server need: `@Serializable` domain models (`data/`), request/response DTOs (`server/request`, `server/response`), the `TmResult<D, E: Error>` type + per-domain error enums (`error/`), caches, and `expect` declarations (`AppLogger`, `AppDir`, `Platform`) with per-platform `actual`s.
- **`composeApp`** — KMP Compose UI + client logic, built as an Android *library* plus `jvm("desktop")`, `wasmJs`, and `iosArm64`/`iosSimulatorArm64` only when Gradle runs on macOS (the `ComposeApp` framework). Every `expect` needs an `iosMain` actual too; nothing on Linux compiles it, GitHub's CI `iOS compile` job does. iOS code was written without a Mac and is untested (`docs/roadmap.md`).
- **`androidApp`** — thin Android application wrapper around `composeApp` (`MainActivity`).
- **`server`** — Ktor JVM app (`EngineMain`, module `ApplicationKt.module`).
- **`iosApp`** — Xcode project (bundle `org.mr0btain.ticketman`, iOS 16+); its build phase runs `embedAndSignAppleFrameworkForXcode` and `ContentView` shows `MainViewController()`. HTTPS trust there is `DarwinTrust` (Security framework) instead of `PinningTrustManager`.

Dependency versions and bundles (`ktorServer`, `ktorClient`, `exposed`, `koin`, `fileKit`) are in `gradle/libs.versions.toml`. Projects are referenced via type-safe accessors (`projects.shared`).

## Architecture

### Domain model pattern
Each main entity (Customer, Ticket, Inventory, User) extends `MainItem` (shared), identified by a `Uuid` whose embedded timestamp is used as the creation time (`identifier.createdAt()`). Entities have attached `Note`s, and notes have `StoredImage`s. This shape is mirrored identically on each layer, so adding a field or entity usually means touching all of them:

1. `shared/.../data/<entity>/` — serializable model
2. `server/.../database/tables/<entity>/` — Exposed DAO tables/entities (plus `<Entity>NoteTable`, join tables), registered in `LocalDatabase.initDatabase()`'s `SchemaUtils.create(...)`
3. `server/.../database/<Entity>Database.kt` — extends abstract `Database<T : MainItem>` (CRUD, paging, notes, images, search), listed in `LocalDatabase.recordDatabases` (the photo sweep and detached note clean up find each type's notes through its `noteLinkColumn`)
4. `server/.../routing/<Entity>Route.kt` — mounted under `/api/data/<entity>` (users under `/api/user`, auth under `/api/auth`, admin dashboard under `/api/admin`, shop profile under `/api/shop`) in `Routing.kt`. Every path is a constant in shared's `server/ApiRoutes.kt` (`ApiRoutes.CUSTOMER`, `RecordPaths.GET`, `NotePaths.ADD`, `TicketPaths.FETCH_MINE`, ...) used by both sides; clients fill `{parameters}` with `fill()`. Reads are `GET` (`/get/{identifier}`, `/fetch?offset=&limit=` via `call.pagedRequest()`, `/search?query=&limit=` via `call.searchQuery()`, `/get/notes/{identifier}`); `/add` answers `201` with the saved record. `check_api_docs.py` reads the constants, so keep them plain strings
5. `composeApp/.../network/database/<Entity>RemoteRepository.kt` — extends abstract `RemoteRepository<T>` (route `ApiRoutes.<ENTITY>`), whose calls all return `TmResult<T, ServerError>`: reads included, so a screen tells `NOT_FOUND` (`ServerError.isNotFound`, `orNullIfNotFound()`) from a failed load. Never turn a failed notes/photos read into an empty list a save could write back
6. `composeApp/.../data/<entity>/` — client-side `*Cache` and `*Seed`. A seed is the record being viewed or edited: each one lists its editable `fields()`, and `isDirty` / `getChangedFields()` compare them against the snapshot `markClean()` took when it was loaded or saved, so changing something back counts as unchanged. A new field only needs adding to `fields()`

### Server
`Application.module()` → `configureDatabase(path)` builds a `LocalDatabase` (H2 file DB at `<path>/server/database/`) exposing one `<Entity>Database` per entity plus `TokenDatabase`. `JwtService`/`UserService` handle login and access/refresh tokens. Passwords and PINs are PBKDF2-hashed by `PasswordHasher` (legacy plain-text passwords are upgraded on login) and users are blanked with `User.withoutPassword()` before leaving the server. Write routes log to `AuditLogDatabase` via `call.audit(...)`; `log()` goes through `dbWrite`, so inside a multi step `transaction { }` (check-in, pickup, void) it's written as that transaction's last step and rolls back with it.

- **Sessions**: one row per device in `TokenTable` (`TokenDatabase`/`StoredSession`). Tokens carry a `sid` claim, a `typ` (`access`/`refresh`) and a random `jti`; the auth providers only take access tokens, valid only while that session row exists for its user and is live (`StoredSession.isLive`: before `expiresAt`, and within a kiosk PIN session's idle limit). Each refresh swaps the refresh token for a new one with the same expiry (`TokenDatabase.rotate`, a compare and set), and the client saves it. The hourly sweep deletes expired sessions (`removeExpired`). A good token whose access level is too low gets `403` (`JwtService.checkAccess` → `AccessCheck.Denied`), anything else turned away `401`. Wrong password logins are capped in memory by `LoginLimiter` (20 per address per 15 minutes; per username 5 free tries then waits doubling from 30 seconds to 15 minutes; past 100 from everywhere each address that guessed wrong waits; `429` with `Retry-After`); locks are audit logged as `LOGIN_FAILED` and listed and lifted on the admin Sessions tab (`/api/admin/logins`). The client sends a stable `deviceId`, so logging in again on the same device replaces its session; other devices are untouched Logins without a `deviceId` keep only the newest 10 sessions per user.
- **Users**: `UserStatus` (PENDING/ACTIVE/DEACTIVATED) is separate from `AccessLevel`; `User.canAccess(level)` is the check (active, setup finished, level high enough). `AccessLevel.NONE` only exists for migrating old data. New accounts come from requests (`/api/auth/request-account`, then admin approve) or invites (setup code used as the password), see `AccountService`. Users with `needsSetup` can only reach routes under the `"setup"` auth provider.
- **PINs and stations**: 6 digit PINs (`PinRules`) lock after 5 wrong tries. PIN login (`/api/auth/pin`) needs an admin-approved station's id + secret (`StationDatabase`); PIN sessions last 12h and each one ends the previous PIN session on that station. Stations can be put in kiosk mode with an idle timeout; a kiosk's PIN session also ends on the server once unused for that timeout plus 10 minutes (the client keeps it alive while someone is using it), and an admin leaving kiosk mode calls `/api/auth/kiosk/leave` to drop that limit.
- **Money**: always `Long` cents (`Money` in shared), shown with the shop profile's `currencySymbol` (the kit's `LocalCurrencySymbol`/`formatMoney` on the client, never a bare `Money.format` on a screen). Invoices (`InvoiceDatabase`/`InvoiceService`) are one per ticket, or a counter sale with no ticket (`POST /api/counter/sale`, `Invoice.isSale`, made paid with its stock taken in one transaction); deleting the ticket deletes an open unpaid one but keeps one with payments or a void one (`ticket_id` is no foreign key; `ticketLabel`/`ticketRemovedAt`), which only an admin deletes (`DELETE /api/invoice/{id}`); totals come from shared `InvoiceMath`, tax from the shop profile's rate when the invoice was made (kept on the invoice after) and its tax classes (`ShopProfile.taxClasses`, kept as `Invoice.taxRates`; a line or inventory item picks one with `taxClass`, a class made later is added when a line first uses it, and the discount is shared between rates). `POST /api/counter/pickup` pays the invoice, takes parts from stock (refusing if there isn't enough) and closes the ticket together. Stock never goes below zero and only changes in single SQL updates: pickup and void through `InventoryDatabase.adjustStock`, and by hand through `/api/data/inventory/set/stock/{id}`, which only writes if the count is still the `from` the client opened it at (409 otherwise). Inventory `/update` leaves stock alone; `InvoiceService` changes that check then write run under its `CHANGE_LOCK`, so two pickups can't both go through. Only pickup sets `PICKED_UP`: ticket add/update refuse it and never change a picked up ticket's status; `POST /api/counter/check-in` makes the ticket, links, deposit and signature together (`CheckInService`), and can take several devices at once (`more`) as tickets sharing a `groupIdentifier`. Each ticket points at the customer's device record (`Ticket.deviceIdentifier`, `customer_devices`/`DeviceDatabase`, endpoints under `/api/data/customer/device*`): the one picked, theirs with the same serial, or a new one. Check-in also saves the intake checklist (`Ticket.checklist`, per `DeviceKind` from `ShopProfile.checklists` or `IntakeChecklists.defaults`) and the device passcode, sealed with AES-GCM under a key from the server secret (`PasscodeVault`, `ticket_passcodes`, `Ticket.passcodeSet`), shown only to Normal users through `/api/data/ticket/passcode/{id}` with each look audited, and cleared in the pickup transaction. Pickup also starts the warranty (`Ticket.warrantyUntil` from shared `Warranty.days` over the lines' `warrantyDays`, else `ShopProfile.warrantyDays`); a check-in with `warrantyOf` (a covered ticket of the same customer) is a warranty return whose logged work is free unless priced. Storage terms (`ShopProfile.storage`, shared `Storage`): `InvoiceService.forTicket` and pickup sync a storage fee line (id from `Storage.lineIdentifier`; removing it sets `storageWaived`), and the hourly `StorageService.sweep` queues the `STORAGE_FEE` notice and marks tickets ready too long as `abandonedAt` (queue's `abandoned` list, `ABANDONED` message). A ticket's work log (`WorkEntry`, `ticket_work`/`WorkDatabase`, `/api/data/ticket/{get,add,remove}/work/{id}`) goes through `InvoiceService.logWork`/`removeWork`: each entry adds an invoice charge with the entry's own id in the same transaction, priced from the request, the shop's `laborRateCents` or the item; only while the invoice is open and the ticket not picked up. Invoice edits (`/api/invoice/{id}/update`) send only what changed since the invoice was opened (`InvoiceChangeRequest` from shared `InvoiceChanges.between`, applied by `InvoiceChanges.apply` under `CHANGE_LOCK`), so work logged meanwhile stays; a line changed on both sides is a `409` and the counter reloads. Refunds (`POST /api/invoice/{id}/refund`, admin) are negative payments with a reason and the parts they put back in stock. Store credit (`Customer.creditCents`, history in `customer_credit`) and gift cards (`gift_cards`, sold as `ChargeType.GIFT_CARD` lines and loaded when the invoice is paid) are `PaymentMethod`s with `storedValue`, kept in `StoredValueDatabase` and spent through `StoredValuePayments` inside the payment's transaction, balances only changing in single SQL updates that can't go below zero.
- **Ticket statuses**: the built-in `TicketStatusType` (IN_PROGRESS/ON_HOLD/DONE/PICKED_UP) drives everything (queue, pickup, stats). Shops add their own as `CustomStatus` in `ShopProfile.statuses`; a ticket in one has `TicketStatus.custom` set and `status` = its `actsAs`, which the server fills in (`CustomStatusRules.resolve` in ticket add/update and check-in) and never lets change once saved. Removing a status keeps it `retired` (`keepingRemoved`), so tickets and history (`ticket_status_history.custom_status`) still name it. Compare statuses with `.choice` (`StatusChoice`), name them with `List<CustomStatus>.label`/`customerLabel` (customers see a custom name only if `showCustomer`). Ticket notes have `customerVisible` (off by default) for the coming status page; `ShopProfile.publicUrl` is where customers reach the server. `docs/roadmap.md` has the phases planned after this.
- **Customer status page**: `/status` (`StatusRoute`, `StatusService`, HTML from `StatusPage`; no scripts, no login), the one part meant for the internet behind a proxy that turns outsiders away from everything else (`docs/operations.md`). Each ticket gets a random hex `statusToken` when added (never the client's; backfilled on start by `backfillStatusTokens`), replaced by `POST /api/data/ticket/status-token/{id}`; the link is `StatusLink.url(publicUrl, ticket)`, the claim slip's QR once `publicUrl` is set, and the counter search takes it. It shows statuses as customers see them (`customerChoice`), `customerVisible` notes and their photos (`/status/{token}/photo/{id}/{thumb|display}`), the estimate and balance, the first name and the shop's contacts, never internal notes or contact details. The lookup form (number + last 4 phone digits) and bad links are limited per address and per ticket number by `RequestLimiter`s.
- **Messages and estimates**: `NotificationService` (`components/notify/`) queues customer messages in the `outbox` table (`NotifyDatabase`) and a 10 second loop sends them through `NotificationSenders.email`/`.sms` (`SmtpEmailSender` on Angus Mail, `TwilioSmsSender` over the JDK `HttpClient`; tests swap in fakes and call `sendDue()` on their own instance), retrying on `SendResult.Retry` with `RETRY_DELAYS`. Automatic messages (ready for pickup and picked statuses from the ticket update route, estimate ready, reminders from the hourly sweep) only go to customers with `notifyEmail`/`notifySms`, for the events in `NotificationSettings.events`; staff sends from the ticket card ignore that. The SMTP password and Twilio token stay on the server (`withoutSecrets`, a null on save keeps the saved one). `EstimateService` sends estimates (one `PENDING` per ticket), takes answers from staff (`/api/estimate`) or the status page's form (typed name as signature), puts approved lines on the invoice with `InvoiceService.addApprovedLines` in the same transaction, and moves the ticket to the profile's `estimateSentStatus`/`estimateApprovedStatus`/`estimateDeclinedStatus` without sending status messages.
- **Card payments**: `components/payments/`, `/api/payment`. `PaymentProcessor` has `StripeProcessor` and `SquareProcessor` (REST over the JDK `HttpClient`, like Twilio) and a `SimulatedProcessor` only allowed in development mode (reader paid after 2s, declined when the amount ends in .02); `PaymentProcessors.factory` is swapped in tests. Settings (`PaymentSettings`, `payment_settings`) keep the keys on the server like the message settings (`withoutSecrets`/`keepingSecretsOf`). Each try is a `CardCharge` (`card_charges`, `PaymentDatabase`), whose status leaves `PENDING` once in a compare and set; it's only marked paid from what the processor answers when asked (`PaymentService.refresh`: each `GET` of a charge, the 10 second `sweep`, the status page on load, webhooks at `/status/payments/{provider}/webhook` only naming what to ask). A paid charge with an invoice becomes a `CARD` payment on it (`InvoiceService.cardCharged`, under `CHANGE_LOCK`, even on a paid or void invoice); one with none waits for a `PaymentRequest.chargeIdentifier` to claim it (`CardPayments.problem`/`claim`, like stored value) in a sale, payment or check-in deposit. `Payment.processor`/`processorReference`/`chargeIdentifier`/`refundOf`: refunds with `RefundRequest.paymentIdentifier`, and removing a processor payment from an open invoice, refund through the processor first. Payment links (`/charge/link`, the status page's `GET /status/{token}/pay`) need `publicUrl`, come back to the status page, and one waiting per invoice and amount is reused. Client: `counter.cards` (`CounterCards`: options, reader charge polling, links), `PaymentPanel`'s reader button, `ReaderChargeDialog`/`PaymentLinkDialog` (kit `TmQrCode`), `admin.payments` and the admin Payments tab.
- **Purchasing**: `PurchaseService` over `PurchaseDatabase` (`suppliers`, `purchase_orders` with lines as JSON), `/api/purchase`. Orders go DRAFT → ORDERED (place) → PARTLY_RECEIVED/RECEIVED (receive puts parts in stock with `adjustStock` and sets the item's cost) or CANCELLED; only drafts change. Lines can be for a ticket (`/orders/part` adds to the supplier's draft): placing moves those tickets to `ShopProfile.partsOrderedStatus`, and the last part arriving to `partsArrivedStatus`, through `TicketMoves` (shared with estimates). Client: `viewModel.purchasing` (`PurchasingHandler`), `Destination.PURCHASING`, the ticket card's Parts panel and low stock's Draft orders.
- **Reports**: `ReportDatabase` (`/api/report`, admin only) sums paid invoices, payments, the work log (a work entry's invoice line has its id, so techs are credited at the billed price) and status history into a `PeriodReport`. Part lines keep the item's cost from when the invoice was paid (`InvoiceDatabase.recordCosts`, `invoice_charges.cost_cents`) for the profit. Commission rates are in `commission_rates`, apart from users so only admins see them. Client: `admin.reports` (`AdminReports`), the admin Reports tab.
- **Appointments**: `AppointmentService` over `AppointmentDatabase` (`appointments`, `/api/appointment`): booked, then `ARRIVED` only through a check-in carrying `appointmentIdentifier` (marked in the check-in's transaction, `markArrived` only from `BOOKED`), or `NO_SHOW`/`CANCELLED`. The hourly sweep queues `APPOINTMENT_REMINDER` (`NotificationService.queueAppointmentReminders`, a message with no ticket) a day ahead. Client: `viewModel.appointments` (`AppointmentsHandler`), `Destination.APPOINTMENTS` ("Calendar"); **Check in** starts the counter's wizard with `CounterCheckIn.startFromAppointment`.
- **Time clock**: `TimeClockService` over `TimeClockDatabase` (`time_entries`, `/api/timeclock`). Clocking toggles in/out under one lock; at a station it's `POST /punch` with a `PinLoginRequest` and no login, checked by `UserService.checkStationPin` (shared with PIN login), from the kiosk lock screen's **Clock in or out** (`KioskHandler.punch`, sent through the unauthenticated `ServerUserClient`); from your own device `/me/punch` (user menu and Settings, `viewModel.timeClock`). Admins read and fix timesheets on the admin Timesheets tab (`AdminTimesheets`).
- **Numbers**: tickets `26-00000042`, invoices `INV-26-00000042` and purchase orders `PO-26-00000042`, per year, assigned under a lock with a unique index. An outer transaction that adds a ticket or invoice (check-in) has to hold the lock until it commits: `tickets.whileNumbering { invoices.whileNumbering { transaction { ... } } }`, ticket lock first.
- **Photos**: bytes live on disk in `ImageStore` (`<dataPath>/server/images/<first 2 chars of id>/<id>/{original,display,thumb}.jpg`), with paths built only from the id and never from client input. Only metadata goes in `ImageTable`. `POST /api/image/upload` (multipart, `ImageLimits`: 25 MB, 50 MP) goes through `ImageService`/`ImageProcessor` (Thumbnailator), which rotates the photo upright from EXIF, strips its metadata, flattens transparency and writes the `ImageVariant` sizes (2560/1600/320, never enlarged). Uploads start `PENDING`, and only the uploader can fetch a pending photo. Saving a note or inventory item links them through `linkImages()`, which only takes photos that are pending or already on that owner. Dropped photos are soft deleted (`DELETED`). Photos never change once uploaded, so `GET /api/image/{id}/{variant}` sends an immutable `Cache-Control` and its hash as the ETag. Never delete photo files directly: mark rows deleted (`markImagesDeleted`) and leave it to the hourly `ImageService.sweep()`, which purges after a day and also removes orphan folders. Notes are edited in place with `/update/note/{id}`; inventory photos are set as a whole list with `/set/images/{id}`.
- **Backup and restore**: `BackupService` builds a zip on disk (`manifest.json`, `database.zip` from H2 `BACKUP`, optionally `images/`; format version 2, whose older archives may hold a `tls/` that restore skips) and returns a `BackupTicket`. Clients build it with `POST /api/admin/backup/start` and poll `/backup/status/{id}` (`BackupService.start`/`job`), since a reverse proxy gives up on a request that's quiet for a minute; the one-request `POST /backup` stays for older clients. `runSchedule()` (hourly sweep) writes the daily one into `BACKUP_DIR` and keeps the newest `BACKUP_KEEP`. Its link `/api/admin/backup/download/{id}?token=` needs no login (the browser can download it directly), lasts 30 minutes, or 5 minutes after it was last used, and supports Range. The database is copied before the photos, which is consistent only because photo deletion is delayed a day. `POST /api/admin/restore` (raw zip body) validates the archive and parks it in `server/restore/`. `RestoreService.applyPending()` runs in `configureDatabase` before H2 opens: it moves `database/` and `images/` to `pre-restore-<time>/`, unpacks the archive, rolling back on failure, and writes `restore/last.json` for the admin screen. The sweep deletes `pre-restore-*` and `restore/failed-*.zip` after `RESTORE_KEEP_DAYS`. Restoring always needs a restart; with `RESTART_ON_EXIT=true` the admin screen's Restart now calls `POST /api/admin/restart`, which answers then exits with code 3 (`ServerRestart`, whose `exit` tests replace) for the restart policy to start it again. On stop (SIGTERM or that exit) Ktor's shutdown hook raises `ApplicationStopped`, which runs `LocalDatabase.close()` (H2 `SHUTDOWN`; the JDBC URL turns off H2's own exit hook). Big bodies are streamed with `copyToFile` / `respondFile`, never `receive<ByteArray>` / `respondBytes`.
- **HTTPS**: always a reverse proxy's job (Caddy in `docker/docker-compose.yml`, `docker/Caddyfile`); the server only answers plain HTTP, `main()` is plain `EngineMain`. `plugins/Proxy.kt` (our own plugin, not Ktor's `XForwardedHeaders`) takes the client's address from the last `X-Forwarded-For` entry only on connections from `TRUSTED_PROXIES` (`components/proxy/ProxySettings`), and `startupNotes` (`StartupLog.kt`) logs the port, the trusted ranges and warnings for the retired HTTPS settings. Caddy serves its local CA's root at `/.well-known/ticketman/ca.pem` for the clients' trust dialog (see Server trust below). Caddy redirects plain HTTP to HTTPS; clients with an `http://` address see the redirect when connecting and move to the `https://` one (`ServerUserClient.httpsRedirectOf`, saved through `SessionHandler`'s `onServerMoved`). `GET /api/ping` answers `TicketMan` and is the clients' up check (`/` stays as the old one when no web client is built in). With `-PwithWeb`, `server/build.gradle.kts` copies `:composeApp:wasmJsBrowserDistribution` into resources `web/` with `.gz` copies, and `webRoute()` serves it at `/`. CORS (`plugins/Cors.kt`) is only installed in development mode.
- **Access**: read routes use `authenticate("restricted")` so Restricted users can look, users included (passwords blanked); writes use the default (NORMAL) provider. `UsernameRules`, `PasswordRules` and `PinRules` are in shared and checked on both sides.
- **Notes**: every record type mounts the shared `noteRoute` (`/add/note/{id}`, `/get/notes/{id}`, `/update/note/{id}`, `/remove/note/{id}`). Update and remove take only the note's id, so `Database` checks the note is on that record type (`noteLinkColumn`) before changing it. Staff notes on users (`/api/user/...`) are admin only for reading and writing, and are saved and deleted straight away by `UserRecords` and shown in the admin Users tab. Notes and their photos are edited and deleted in the kit's `TmEditNoteDialog`; on records the change is only sent when the record is saved, and record dialogs keep Save off until `seed.isDirty`.
- **Migrations**: `LocalDatabase.initDatabase()` creates tables, then adds missing columns only for tables in `migratedTables` (add a table there when you give it a column; new columns need a default or nullable). Columns on the `user` table go in `addUserColumns()` because H2 can't list that table's columns (reserved word). Avoid reserved column names (`condition` is stored as `device_condition`). Data fixes run after (`backfillNumbers`, `migrateDeactivatedUsers`, `clearLegacySessions`, `backfillExpiry`, `migrateLegacyPrices`, `removeDetachedNotes`); ones that would wrongly change data typed later or only make sense once (like `legacy-names`, which rewrites old `first:last` lowercase names, and `invoice-ticket-key`, which drops the old invoice to ticket cascade) go in `runOnce(name)`, recorded in `DataFixTable`. Names are stored as typed and shown as they are. `plugins/Security.kt` registers three JWT auth providers keyed to `AccessLevel`: default (`NORMAL`), `"restricted"`, and `"admin"`; routes wrap handlers in `authenticate { }` / `authenticate("admin") { }`. `routing/Helpers.kt#getIdentifierFromToken()` extracts the calling user's UUID from the JWT.

### Client
- DI: Koin, started in each platform entry point via `initKoin()` with `viewModelModule` and `dataModule`.
- `ui/MainViewModel` is the app-lifetime state holder. It owns the `RemoteHandler` and wires together handlers that each own one part of the app, connected through callbacks: `CustomerRecords`/`TicketRecords`/`InventoryRecords`/`UserRecords` (`viewModel.customers` etc., in `ui/screens/records/components/<entity>/`: each entity's cache, `OffsetPager`, seed, selection, save, remove and search; notes sync through `syncNotes` in `RecordNotes.kt`, which sends only this device's changes since the record was opened (`seed.savedNotes`) and won't overwrite another device's edit), `SessionHandler` (`viewModel.session`: connecting, login/logout, the logged-in `currentUser`/`isAdmin`/`canEdit`, account requests and setup, this device's station), `SettingsHandler` (`viewModel.settings`: saved settings, each change written to `LocalStorage`), `AdminHandler` (admin screen: overview, low stock, audit, with parts `accounts`, `devices` (stations, sessions, blocked logins), `server` per tab group, and `import` for CSV imports, whose preview is the server's own `?dryRun=true` answer from `ImportService`), `CounterHandler` (counter: search, queue, ticket and customer cards, price check, with parts `checkIn`, `pickup`, `invoices`, `printer`) and `KioskHandler` (kiosk mode, PIN lock, idle timer). A handler's parts share a small `<Area>Support` (scope, snackbar, ...) and reach the handler only through callbacks it passes them; split a handler the same way once it grows past a few hundred lines. `CounterHandler` and the customer, ticket and inventory records handlers take `canEdit` and refuse changes for Restricted users, and their screens hide the buttons (`TmPanelTopBar(canChange = false)` shows a "View only" badge, `RecordDetail(canEdit = false)` drops Edit); the server still refuses the write.
- Counter screen is `ui/screens/counter/`. Kiosk mode (`ui/screens/kiosk/`) replaces the whole app with the counter and a PIN lock screen; it turns off `RemoteHandler.credentialFallback` so a locked kiosk can't log the owner back in, and sets `ui/AppWindow.fullscreen`, which each platform entry point applies; Android's `MainActivity` also pins the app with lock task mode and reports it in `AppWindow.pinned`, and `KioskShell` offers to pin again while it's unpinned.
- Photos: `ImageClient` (handed to composables via `LocalImageClient`, null in previews and render tests) uploads picked files; only Android shrinks them first, because FileKit's desktop compressor ignores EXIF orientation. It also builds the Coil `ImageLoader`, set as the singleton in `App`, which fetches through `RemoteHandler.httpClient` so photo requests carry the bearer token, with a 250 MB disk cache via `imageDiskCache()` (none on web). Show photos with the kit's `TmImage` / `TmImagePager` / `TmImageView` (and people with `TmAvatar`) and edit them with `TmPhotoEditor` (all in `ui/kit/images/`). Users have one profile photo (`User.photo`, `UserTable.photo`, set through `/api/user/set/photo/{id}`, admins for anyone and Normal users for themselves; the sweep counts it as in use) and an ID card code (`UserTable.badgeCode`, `BadgeCode` in shared, admin only through `/api/user/badge/{id}`), printed with `PrintTemplates.idCard` from the admin Users tab.
- Large transfers: the HTTP client logs headers only (logging bodies buffers them) and has a 60s request timeout. Long uploads and downloads call `transferTimeout()`. `components/network/transfer` holds `downloadTo` (streams to a kotlinx-io sink), `saveDownload` (file saver on desktop/Android, browser download on web) and `fileBody` (streams a picked file as a request body; web reads it whole). Use these rather than `readRawBytes` + `saveFile` for anything that can be big.
- Printing: `components/print/PrintTemplates` builds a platform-neutral `PrintDocument`; `printDocument()` is expect/actual (desktop: Java2D `PrinterJob`; web: hidden iframe of `HtmlPrintRenderer`; Android: WebView + `PrintManager`, needs `AndroidPrintHost.attach` from `MainActivity`). `QrCode` and `Code128` (barcodes, `PrintBlock.Barcode`, on item labels from `PrintTemplates.itemLabel`, `PaperSize.LABEL`) are in-house encoders. A scanner is a keyboard that presses Enter: the counter search and the part searches look the code up exactly on Enter (`GET /api/data/inventory/code/{code}`). `PrintBlock.Photo` carries JPEG bytes (Java2D draws it, HTML inlines it). `PrintDocument`, `PrintTemplates`, `QrCode` and `Formatting.kt` live in `shared` (same packages) and `Java2DPrintLayout` in `shared`'s `jvmMain`, because the server makes invoice PDFs from them (`InvoiceDocuments`: the layout drawn through PDFBox's `PdfBoxGraphics2D`, `GET /api/invoice/{id}/pdf`; the CSV export is `GET /api/invoice/export?from=&to=&format=`, admin only: `invoices` from `InvoiceDocuments`, or `quickbooks`, `xero` and `payments` from `AccountingExport`, named from `ShopProfile.accounting`). The client reads those two whole and saves with `saveFile`, since a browser download wouldn't send the login header.
- Times on screen go through `components/utils/Formatting.kt` (in `shared`; local time via kotlinx-datetime).
- `RemoteHandler` builds a Ktor client (with bearer-token auth/refresh using `LocalStorage`) and holds one remote repository per area, all in its `repositories` list (`ServerRepository`); `setUrl()` verifies the server is reachable and propagates the base URL to every one. Repositories no-op when `serverUrl` is blank. `/api/ping` sends `X-TicketMan-Version: <APP_VERSION>` (shared `server/AppVersion.kt`, from `ticketman.version` through the `BuildInfo` shared generates) and `X-TicketMan-Api: <API_VERSION>`; `versionNoticeOf` compares them with the client's: a major version apart (a minor before 1.0) is `ConnectionResult.INCOMPATIBLE`, no repository gets the address and `UpdateRequiredScreen` takes the app (`SessionHandler.updateRequired`); a minor apart, or another `API_VERSION`, is a `SessionHandler.versionNotice` warning (snackbar plus a notice on Settings > Account). Every client request carries its `X-TicketMan-Version` (`sendAppVersion`), and the server answers `/api/` calls (not the ping) from one a major version away with `426` (`plugins/ClientVersion.kt`, no header passes); a 426 mid-session makes the client reconnect (`RemoteHandler.versionRejected`). Bump `API_VERSION` for a change older clients can't use, and the major (minor on 0.x) for a release they can't. `OffsetPager` takes a `TmResult` per page and exposes `loadError`, shown over the records lists.
- `LocalStorage` persists settings/tokens through a `KeyValueStore` (KSafe-backed; `InMemoryKeyValueStore` in tests).
- UI: every screen is built from the UI kit (below). `ui/screens/navigation/AppShell.kt` frames the app: a glass nav rail on wide windows (`WideAppShell`, with the user menu and log out at its foot) or a glass bottom bar on phones (`PhoneAppShell`), the backdrop behind everything and the snackbar host. The records screen (`ui/screens/records/`, `Destination.RECORDS`) is one `RecordsLayout` per entity: toolbar (the kit's `TmPanelTopBar`), list, and details, stacking on narrow windows.
- Server trust: addresses with no scheme mean `https://` (`normalizeServerAddress`); addresses saved before HTTPS get `http://` added once when `LocalStorage` loads. Plain `http://` still connects, but off this machine (`isSecureServerAddress`) `SessionHandler.insecureWarning` shows "Not secure" (snackbar, login popup, Settings > Account). Desktop and Android share `jvmSharedMain` (a `jvmShared` group in `applyDefaultHierarchyTemplate`), which holds the OkHttp engine: `PinningTrustManager` accepts what the system trusts plus chains from the one private CA `ServerTrust` holds per `host:port` (`TrustedAuthority`, fingerprint and certificate), and refuses anything else into `ServerTrust.refused`, offering the proxy's CA (fetched from `ServerTrust.AUTHORITY_PATH` and checked to have signed the chain) or else the top certificate sent, since Caddy's own certificate changes every 12 hours. `setUrl` then returns `ConnectionResult.UNTRUSTED`, and `App` shows `ServerTrustDialog` (warns it's not a public certificate) for `SessionHandler.untrustedCertificate`; trusting saves it (`trusted_authorities`). Web uses Ktor's Js engine and the browser decides. Test mocks must answer `SERVER_PING_PATH` with `SERVER_PING_BODY`.
- Platform specifics go through `expect`/`actual` (`getHttpEngine`, `defaultServerAddress` (`http://localhost:8080` on a desktop debug build), `IsDebug`, `alwaysWide` (desktop always gets the nav rail), `InitAppDir`, `TmVerticalScrollbar`, `AppLogger`, `saveFile`, `printDocument`, `shrinkForUpload`, `imageDiskCache`, `saveDownload`, `fileBody`).
- Only Android tasks need the Android SDK: AGP looks for it when one runs, so the server, desktop and web builds work without one (the release workflows' server and DEB jobs don't install it). `androidApp` currently needs compileSdk 37 to build (FileKit 0.16 requires it); `shared` and `composeApp` compile for Android with `:composeApp:compileAndroidMain`. Building the APK needs an AAPT2 that runs on the build machine (the x86 Linux one Gradle downloads fails on ARM Linux). Android has been run end to end in the emulator (`adb reverse tcp:<port> tcp:<port>` reaches a dev server as `localhost`), web in headless Chromium. Android's regex engine is ICU, which rejects patterns the JVM takes (escape `}`). Android is edge to edge: the shells pad by `shellInsets`. The counter only autofocuses search and shows F-key hints while the input mode is keyboard (`usingKeyboard()`/`keyHint()`). `isDebug()` is the debuggable flag on Android, a `localhost` page on web, and `-DticketmanDebug=true` on desktop.

### UI kit
All shared UI lives in `composeApp/src/commonMain/.../ui/kit/`, prefixed `Tm`: `theme/` (tokens), `foundation/` (backdrop, glass and solid surfaces, hover/press/focus, control sizes, scrollbar), `buttons/`, `inputs/` (text, money, PIN, password, signature), `selection/` (dropdown, menu, segmented, chips, toggles), `search/`, `containers/` (panel, dialog, confirm, confirm delete, text edit and full screen dialogs, page and pane headers, list rows, tabs, lazy and scroll columns), `feedback/` (badges for ticket status, priority, access, notices, snackbar, empty and loading states), `data/` (stat tiles, tables, money and ticket number text, key value rows), `images/` (photo, pager, full screen viewer, photo editor), `notes/` (note block, edit note dialog), `navigation/` (rail, top bar, records panel top bar, bottom nav, stepper) and `gallery/` (the component gallery, opened from Settings > Appearance, and in the nav on debug builds).
- Screens get colors, type, shapes and spacing from `TmTheme.colors/typography/shapes/spacing` and never hard code them. `UiKitRulesTest` fails on `Color(0x`, named colors like `Color.Red` (not `Transparent`/`Unspecified`), `fontSize =`, `TextStyle(`, `RoundedCornerShape(`, `MaterialTheme.`, Material 2 imports, or Material 3 imports (other than `Text`, `Icon`, `SnackbarHostState` and the `windowsizeclass` package) outside `ui/kit`, ignoring comments and strings. Need something new? Add it to the kit and the gallery, then use it.
- Themes: `TmPalettes` (Bench default, Copper, Mono), each with dark and light `TmColors`; add one by adding a `TmPalette` to `TmPalettes.all`. Fonts: `TmFonts` (Barlow default, Atkinson Hyperlegible, System); add one by putting its `.ttf`s in `composeResources/font` and a `TmFont` in `TmFonts.all`. Numbers (ticket and invoice numbers, money, PINs, SKUs) always use the `numeric*` styles (JetBrains Mono). The picked theme, font, dark mode and reduce transparency are saved in `LocalStorage` and exposed by `SettingsHandler`.
- Glass: `TmBackdrop` owns a Haze state and draws the background glow; `TmGlassSurface`/`Modifier.glass()` blur whatever sits behind them, `Modifier.glassSource()` marks content (like a scrolling list) for glass on top to blur. Glass is for floating layers only (rail, bars, dialogs, menus, snackbar); cards and lists use solid `TmSurface`. Reduce transparency turns glass solid.
- Ticket statuses show as `TmStatusBadge(ticket.status.choice)` and are picked with `TmStatusPicker`; both read the shop's own statuses from `LocalTicketStatuses` (provided in `App` from the shop profile). Built-in wording is shared `TicketStatusType.label` ("Ready for pickup" for DONE); tones come from `TmColors.tone(...)` of a shared `StatusTone`, so a state keeps its color across themes.

### Conventions
- Naming: UI used by more than one screen is a kit component, `Tm`-prefixed, in `ui/kit` with a gallery entry. Classes extending an abstract base get no `Impl` suffix (`TicketDatabase`, `TicketRemoteRepository`). Platform files are `<Name>.<platform>.kt` next to a common `<Name>.kt` holding the `expect`. Route files are singular, `<Area>Route.kt` with `fun Route.<area>Route()`. Each screen's state lives in an `<Area>Handler` under that screen's `components/`.
- Logging uses `AppLogger.{e,d,i,m}(tag, message)` with hierarchical string tags declared as constants at the top of each class, e.g. `"$TAG:GetById"`. Follow this pattern in new code. `d` only writes when `AppLogger.debug` is on (set from `isDebug()` in `initKoin`, and from development mode on the server).
- Errors: wrap client network calls in `networkRequest(TAG) { ... }` (a `TmResult` saying whether it timed out, couldn't connect or got an unreadable response; pass it to `handleActionHttpResponse`/`handleDataHttpResponse`) or `networkErrorTryCatch(TAG) { ... }` (value or null, for reads), shared code in `appLogTryCatch(TAG) { ... }`, and return `TmResult`/`SimpleResult` rather than throwing. Every error enum implements `Error` (which carries a readable `message`), so any of them can go in a `TmResult`.
- Server DB access goes through `dbQuery(TAG) { ... }` (returns the value, null on failure) and `dbWrite(TAG) { ... }` (returns whether it happened; the block returns false when the row isn't there) in `database/DbCall.kt`. Write methods return that `Boolean` and routes answer 404/500 from it instead of always 202. Inside an outer `transaction { }` (check-in, pickup) they let throws through, so the whole thing rolls back. Every server database uses them; `appLogTryCatch` is for shared code. A failed list or search read answers `500`, not `404`.
